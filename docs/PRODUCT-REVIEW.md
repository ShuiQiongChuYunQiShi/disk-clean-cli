# disk-clean 产品评估与整改方向（2026-09-12）

> **依据**：v0.7.0 发布后的实测复评。本文所有结论都附**可核验证据**（命令、文件、行号），
> 与"看法"区分开。标注「推理」的是未直接验证的判断。
>
> 与 `docs/PLAN-v0.7.md` 的关系：那份是**已完成的**迭代计划；本文是**面向 v0.8 及以后**的
> 产品级评估，覆盖功能性不足之外的**可用性、状态模型、能力一致性、文档真实性**。

---

## 1. 现状与核心问题

### 1.1 已经做得不错的部分（先说清楚基线）

| 维度 | 证据 |
|---|---|
| 安全默认 | 破坏性操作默认 dry-run；移入回收站；16 段受保护路径单源（`lib/guard.js`） |
| 单一事实源 | 版本（`lib/version.js`，9 源守门）、安全闸门、盘符容量（`lib/drives.js`）、去重映射 |
| 测试规模 | 12 套件全绿，含 `safety-gates`（23 断言）与 `cli-and-config`（7 断言） |
| 发布链路 | 双渠道（GitHub + npm），校验和**下载回本地复算**，CI 绿 |
| MCP 工具描述 | 面向 AI 写得相当具体（含安全语义与"省略则如何"的行为说明） |

### 1.2 核心问题一：**测试会破坏用户的真实数据**（P0，本次新发现）

**证据**：

```
$ node bin/disk-clean.js report
  根目录 : C:\Users\ADMINI~1\AppData\Local\Temp\dsk-org-mRVryC   ← 测试树的扫描结果
  总大小 : 1.0 MB  文件: 1  目录: 4
```

```
真实审计日志：总 60 条，其中 44 条操作的是临时测试树（73%），
且含大量 empty-dirs/move-to-recycle-bin —— 即测试真的往用户回收站删了东西
```

**根因**：11 个测试套件中**只有 3 个**隔离了 `USERPROFILE`（`cli-and-config`、`dsh-config`、
`mcp-protocol`）；其余 8 个（`engine-smoke`、`engine-edge`、`clean-safety`、`organize-safety`、
`serve-integration`、`rules-integrity`、`version-consistency`、`ci-workflow`）直接读写
**用户真实的 `~/.disk-clean/`**。

**后果**（三条都实际发生）：

1. 用户的**扫描报告被覆盖**成测试树的扫描结果；
2. **审计日志被污染**——审计是安全特性（用于证明"工具到底动过什么"），现在混入了 73% 的测试记录，
   其证明力被破坏；
3. 用户的**回收站里被丢进测试文件**（实测 `totalInBin=15`）。

> 这不是"测试不够干净"的小事：它意味着**维护者每跑一次 `npm test`，就用测试数据覆盖用户的工作产物**。
> 若用户正基于那份报告做清理决策，后果由测试引入。

### 1.3 核心问题二：**报告没有"出处"，也没有历史**（P0 关联）

- 终端 `report` 输出**不含生成时间、扫描范围之外的任何来源信息**；
  Markdown 文件里有「生成时间：…」，两者不一致。
- 报告是**全局单例** `~/.disk-clean/report.json`，任何一次扫描都直接覆盖上一次。
- 没有任何"报告太旧了"的提示。用户拿到一份 3 天前的报告，界面上看不出来。

**放大风险**：`clean` 等命令的候选路径与范围校验**都来自"最近报告"**。报告被意外替换后，
用户看到的是另一棵树的候选，却又说不清为什么。

**关联发现**：`retention.reports`（默认 30，"保留最近 N 份报告"）**没有任何读取点**——
即"报告历史"这个本该解决上述问题的功能，配置项早就写好了，但从未实现。

### 1.4 核心问题三：**配置面仍有 3 个死键，且 AI 工具描述里仍在承诺**（P1）

逐项核对 `lib/config.js` 的全部 10 个叶子键（除 `config.js` 自身外的全部 lib/bin 源码中查找读取点）：

| 键 | 状态 | 读取点 |
|---|---|---|
| `version` | ✓ | — |
| `exclude` | ✓ 生效 | `engine-core.js:786` |
| `thresholds.looseMinBytes / looseMinDays` | ✓ 生效 | `engine-core.js:784-785` |
| `thresholds.staleMinBytes / staleMinDays` | ✓ 生效 | `engine-core.js:781-782` |
| `thresholds.dupMinBytes` | ✓ 生效 | `engine-core.js:783` |
| `retention.auditLines` | ✓ 生效（v0.7.0 修复） | `audit.js:38` |
| **`retention.reports`** | **✗ 死配置** | 无 |
| **`junkRules`** | **✗ 死配置** | 无 |
| **`organizeRules`** | **✗ 死配置** | 无 |

**⚠ 自我纠正**：v0.7.0 我按锐评把 `blacklist` 删了、把 `auditLines` 修了，
**但同一个类别的另外 3 个键没查**。更严重的是：我在 v0.7.0 重写的 `disk_config` 工具描述里
**明确写着**"保留策略（auditLines/reports）、自定义垃圾规则与整理映射"——
**又把 3 个死配置承诺给了 AI**。这说明当时的修复是"照清单修"而不是"按类别排查"。

### 1.5 核心问题四：**文件分类在真实磁盘上基本失效**（P1，用户可感知）

用真实 D 盘报告（`windowsClear/D盘扫描分析报告.md`，588.32 GB）核对规则表：

```
最大分类：其他 450.48 GB = 76.6%      ← 榜首是"未分类"
```

逐扩展名核对规则表（125 个扩展名）后，**占用 Top 22 中 12 个无分类，合计约 401 GB（约 68%）**：

| 扩展名 | 占用 | 分类 |
|---|---|---|
| `.pak` | **296.88 GB** | ✗ 无 |
| `.safetensors` | 41.87 GB | ✗ 无 |
| `.bin` | 18.05 GB | ✗ 无 |
| `.dat` | 13.55 GB | ✗ 无 |
| `.pgf` `.lib` `.enc` `.dsv` `.ckpt` `.pack` `.apk` `.hprof` | 合计约 31 GB | ✗ 无 |

占全盘一半的 `.pak`（游戏资产包）没有分类。**"文件分类"是 README 的头部卖点，
但在用户真实的盘上，最大的分类是"其他"** —— 这个功能对最需要它的场景（游戏/模型占满盘）
恰恰不产生信息。

### 1.6 核心问题五：**界面在显示机器标识符**（P1）

```
── 智能建议 ──
  [created-old] created-old — 1 项 (1.9 MB)      ← 类型名被打印了两遍
  [junk-temp] junk-temp — 3 项 (1.5 KB)
  [empty-dirs] empty-dirs — 9 项
```

**根因**：引擎生成建议时**不带 `label` 字段**（实测 `report.suggestions[].label` 全为 `undefined`），
CLI 用 `s.label || s.type` 回落，于是显示裸类型。

- 而 **README 展示的是** `[organize-folders] 目录整理建议 — 13 项`——**文档与实现不一致**，
  且 README 里的 `organize-folders` / `recycle-bin` 建议类型在当前实现里已不存在。
- **MCP 侧同样没有 label**：`disk_scan` 不输出任何人类可读的分类说明，
  AI 拿到的只有 `{type:'junk-temp', estBytes:…}` —— 得靠猜。

### 1.7 核心问题六：**能力分布不均匀**（P1，结构性）

同一件事在不同入口的可用性不同，v0.7.0 刚修掉一批（`clean stale-large`、`dedup rollback --yes`），
但**结构上没有约束机制**——没有"能力矩阵"文档，也没有测试守住三处一致。已观察到的差异：

| 能力 | CLI | MCP | GUI |
|---|---|---|---|
| 扫描 | ✓ | ✓ | ✓ |
| 扫描范围确认（防误扫） | ✗ | ✗（靠 roots 校验） | ✓ 弹窗 |
| 进度反馈 | ✓ 状态行 | ✗（同步阻塞） | ✓ 进度条 |
| `drives` | ✓（v0.7.0 补） | ✓ | ✓ |
| 报告历史 | ✗ | ✗ | ✗ |
| 报告出处/时间戳 | ✗ | 部分 | ✓ |

**根因**：同源只做到了**计算同源**（guard/version/drives 单一实现），
没有做到**能力同源**。而"四种形态 × 两语言"的维护面积由单人承担，
每加一处能力要同步 4 处——这正是 A3/A6/A7 与 v7 那批不一致问题**反复发生**的结构性原因。

### 1.8 核心问题七：可用性细节（P2）

| 现象 | 证据 | 影响 |
|---|---|---|
| 缺参数报 `undefined` | `disk-clean clean` → `✗ 未知清理类型: undefined` | 用户不知道是"没给类型"还是"类型错了" |
| 拼错无建议 | `disk-clean clean junk` → `未知清理类型: junk`（应为 `junk-temp`，编辑距离 1） | 多一轮试错 |
| `--lang en` 只影响报告 | CLI 仍输出「▶ 正在扫描」「✔ 扫描完成」「根目录」 | 英文 README 与中文 CLI 不匹配 |
| GUI 恒定提权 | `app.manifest` 为 `requireAdministrator` | 每次启动弹 UAC，而**常规扫描不需要管理员**（只有 mftscan/quota/health 需要） |
| 首次使用无引导 | 无 `doctor`/自检命令；文档要求用户自己知道先 `scan` | 新用户不知从哪开始 |

## 2. 整改方向

按"**先修会伤到用户的，再修对调用方撒谎的，最后修不好用的**"排序。

### 2.1 R1 —— 状态隔离与报告溯源（对应 1.2 / 1.3）

- **R1-1 测试全面隔离**：给全部 12 个套件注入 `USERPROFILE/HOME` 到临时目录
  （已有实现可复用：`mcp-protocol.js:20`）。并**加一条测试守卫**：
  在真实 HOME 下记录 `~/.disk-clean/` 的文件指纹，跑完 `npm test` 后断言未被改动——
  防止将来新增套件又忘记隔离。
- **R1-2 报告加溯源**：`report.json` 写入 `{generatedAt, version, roots, elapsedMs, tool}`；
  CLI/MCP/GUI 的**每一处**报告输出都必须显示生成时间与范围；超过阈值（如 24h）
  显示「报告已生成 X 小时前」提示。
- **R1-3 报告历史**：实现 `retention.reports`（配置项早就在，只是没接线）——
  每次扫描归档到 `~/.disk-clean/reports/<ts>.json`，保留最近 N 份，
  `report --list` / `report <ts>` 可读取历史。这同时解决"测试覆盖后无法回溯"。

### 2.2 R2 —— 把"要么实现要么删"贯彻到全部配置面（对应 1.4）

- 对 `retention.reports` / `junkRules` / `organizeRules` 逐个决定：**实现或删除**。
  建议：`retention.reports` **实现**（R1-3 正好需要）；`junkRules` / `organizeRules`
  **实现**（它们对"分类失效"这一核心痛点是直接解法——见 R3），否则**立即从
  `DEFAULT_CONFIG` 与 `disk_config` 工具描述中删除**。
- **加一条守门测试**：遍历 `DEFAULT_CONFIG` 的每个叶子键，断言它在
  lib/bin 源码中**至少有一个读取点**（本次核对用的脚本可直接沉淀为测试）。
  这条测试能永久防止"配置项写了没人读"复发——本次 4 个死键中有 3 个是它抓出来的。

### 2.3 R3 —— 分类规则面向真实占用重建（对应 1.5）

- **数据驱动补规则**：以真实扫描的"最大文件 + 最大扩展名"为输入，补齐
  **游戏资产**（`.pak/.pack/.ucas/.utoc/.vpk/.assets`）、**AI 模型**
  （`.safetensors/.ckpt/.gguf/.onnx/.pt/.pth/.bin` 需按目录语境区分）、
  **容器/虚拟盘**（`.vmdk/.vhdx/.qcow2`）、**开发产物**（`.hprof/.lib/.pdb/.obj`）。
- **加"未分类 Top"输出**：报告主动列出占用最大且未分类的扩展名，
  让规则缺口**自己暴露**而不是变成"其他 76.6%"。
- **目标**：在真实盘上把"其他"压到 **< 30%**，并把该指标纳入发布前验收
  （用一份固定的真实占用样本作基线）。

### 2.4 R4 —— 能力矩阵与一致性守门（对应 1.7）

- 写出 **`docs/CAPABILITY-MATRIX.md`**：一行一个能力，列出 CLI / MCP / GUI 的可用性与
  不对称的**理由**（例如"扫描范围确认"在 CLI 无交互，改为强制 `--roots` 或列出计划）。
- 把 v0.7.0 的教训固化为测试：`test/cli-and-config.js` 已开始做这件事，
  继续扩展到"每个 MCP 工具都有对应的 CLI 路径，反之亦然"。

### 2.5 R5 —— 文档必须与实现同源（对应 1.6 及多处）

- README 的示例输出、建议类型名、套件数量等**凡是可被程序生成的，就不要手写**：
  加一个脚本从真实运行输出生成 README 的示例块，或至少在 CI 中断言示例与实际一致。
- 本次已发现 3 处文档与现实不符：README 建议输出（label 与类型名）、
  README 里已不存在的建议类型、以及我在 v0.7.0 的 `disk_config` 描述（承诺 3 个死配置）。

## 4. 提升易用性的具体措施

按"改动成本 vs 用户可感知度"排序，全部可执行。

### 4.1 错误消息与引导（低成本、高感知）

| # | 现状 | 改为 |
|---|---|---|
| E1 | `clean` 无 type → `未知清理类型: undefined` | `缺少清理类型。可选：junk-temp / empty-dirs / duplicates / stale-large / recycle-bin`（并给出示例 `disk-clean clean junk-temp`） |
| E2 | `clean junk` 无建议 | 加"最接近的匹配"：`是否想用 junk-temp？`（编辑距离 ≤2 即可） |
| E3 | `scna` → `未知命令: scna` | 同样给最接近命令建议 |
| E4 | 无首次引导 | 新增 `disk-clean doctor`：检查 Node 版本、权限、状态目录可写、报告是否存在且新鲜、回收站可访问，逐项给出**下一步命令** |
| E5 | `report` 无时间/范围提示 | 输出头部加「生成于 X（Y 小时前）｜范围：…｜版本 vX」 |

### 4.2 破坏性操作的可读性（安全相关，应优先）

| # | 措施 |
|---|---|
| E6 | **CLI 扫描前范围确认**：非交互环境下打印"将扫描：C:(已用 373G) D:(已用 600G)，共 N 项"，超过 1 个盘或超过阈值时要求 `--yes`（与 GUI 的弹窗对等） |
| E7 | **清理预览给出"可释放"合计与风险分级**（低/中/高），并把低风险项合入"一键安全清理" |
| E8 | dry-run 输出**已列出路径**（v0.7.0 已做）→ 继续补：显示每项的大小与风险标签 |

### 4.3 长任务的可观测性

| # | 措施 |
|---|---|
| E9 | 扫描进度加**百分比/ETA**（已知总量时可算），并区分阶段（遍历/哈希/建议）——当前只有文件数与字节数，用户无法判断"还要多久" |
| E10 | 输出在**非 TTY**（重定向/管道）时自动降级为逐行日志，避免 `\r` 把日志撑爆 |
| E11 | MCP 的 `disk_scan` 是同步阻塞（整盘扫描可达数分钟），应改为**返回 jobId + 轮询**，与 GUI 的 `--progress` 机制统一 |

### 4.4 国际化

| # | 措施 |
|---|---|
| E12 | 让 `--lang en` 真正作用于 CLI 文案（当前只影响 Markdown 报告）——要么实现，要么把英文 README 降级为"文档英文、界面中文"的明确说明 |
| E13 | 建议类型的人类可读名称进 i18n 字典（现在字典里**根本没有**这些键，见 1.6） |

### 4.5 GUI 与分发

| # | 措施 |
|---|---|
| E14 | **GUI 不再恒定提权**：`app.manifest` 改 `asInvoker`，仅在需要时（mftscan/quota/health）通过重启提权按钮触发；消除每次启动的 UAC 摩擦 |
| E15 | 首次启动向导：默认只选数据盘（已有）之外，补一句"扫描是只读的，不会修改任何文件" |

## 5. 优先级与实施建议

### P0 —— 立即（本轮就应做，不等 v0.8）

| 项 | 理由 | 成本 |
|---|---|---|
| **T1 测试隔离 HOME + 守门测试** | 每跑一次测试就覆盖用户报告、污染审计（73%）、往回收站丢文件。**这是当前唯一会主动破坏用户数据的缺陷** | 低（8 个套件各加一行 env + 1 条守门测试） |
| **T2 `report` 显示生成时间与范围** | 报告是全局单例且无出处，用户可能基于陈旧数据做清理决策 | 低（两处输出各加一行） |

### P1 —— 可信数据（原标 v0.8；按版本规则归入 **0.7.1**）

### 建议的实施顺序与理由

```
T1 ─┬─→ T2 ─→ T3 ─→ T4 ─→ T5        （v0.8：先把"数据可信"做扎实）
    │
    └─→ T6 ─→ T7 ─→ T8              （v0.9：让分类真的有用）
                    └─→ T9..T13      （v1.0：打磨体验）
```

**为什么 T1 排第一**：其余问题的后果是"不好用"或"误导"，而 T1 的后果是
**用测试数据覆盖用户的真实工作产物**——且它对用户是静默的。修它只需极低成本。

**为什么 T6（分类）应是 v0.9 的头号任务**：软件的头部卖点是"分类 + 建议"，
而在真实磁盘上最大的分类是"其他"（76.6%）。当用户最需要它给答案时（游戏/模型占满盘），
它给不出信息。**这一项对"好不好用"的影响大于任何 UI 打磨。**

### 需要产品决策的点（建议明确写下来）

1. **四种形态是否都要长期维护？** 单人维护 4 形态 × 2 语言是 A3/A6/A7 与 v7 那批
