# SOP 升级计划 —— 参考 navigator 项目

> **来源**：`D:\学习\newCode\navigator`（多服务生活管理系统）的研发/部署/运维 SOP 体系。
> **本文件目的**：拆解它的**机制**（而非照抄内容），挑出对 disk-clean 这类
> **单机、单人维护、Windows 桌面工具**真正可移植的部分，形成整改计划。
>
> **核心结论**：navigator 的 SOP 之所以有效，不是因为文档写得多，
> 而是因为**它把流程做进了工具**——审批、自检、版本分析、部署编排都是命令，
> 文档只是说明书。disk-clean 目前恰好相反：**流程全在文档里，靠人和 AI 记住并自觉遵守**。

## 1. navigator 的 SOP 体系拆解（机制层）

### 1.1 统一入口：一个 CLI，双通道（人 + AI）

```
.nav/  src/cli.ts        CLI 入口
       src/commands/     薄路由（doctor / ops / deploy / dev / db / health / inspect / release / analyze ...）
       src/core/         领域逻辑：唯一实现（CLI 与 MCP 共享）
       src/mcp/tools.ts  注册为 MCP 工具（nav_ssh / nav_sql / nav_deploy ...）
```

- **开发约定明文规定**：新增能力 = 「core 层实现 → commands 接线 → mcp/tools 注册」三处联动。
- 人的入口是 CLI，AI 的入口是 MCP，**同一份 core**，行为不可能不一致。
- 平台无关：任何 MCP 客户端（zcode / codex / Claude Desktop）用同样方式注册。

> 对照 disk-clean：`bin/disk-clean.js` + `lib/mcp/` 已经是这个结构，
> 但**只覆盖了"产品能力"**（scan/clean/…），**研发与发布能力完全不在工具里**——
> 它们散在 7 个 `.ps1` 脚本里，靠人记执行顺序。

### 1.2 审批门禁（最值得学的一环）

`core/approval.ts`，设计要点：

| 设计 | 说明 |
|---|---|
| **守卫逻辑平台无关** | 注释原文："守卫逻辑 100% 在此，不依赖任何 AI 平台的 question 机制" |
| **人与 AI 两条确认通道** | 人：CLI 交互输入 `DEPLOY` → 写审批文件；AI：传 `--approval-file <path>` → 只做校验 |
| **校验三要素** | `confirmed=true` + **服务/版本精确匹配**（支持数组与 `all`）+ **30 分钟时效** |
| **失败原因具体** | 例如"审批已过期（35 分钟前确认，超 30 分钟）"、"审批版本不匹配：v2.0.0 vs v2.0.1" |
| **审批即同步** | 审批通过自动 sync 内部版本到线上，防"部署了但漏同步" |
| **留痕** | 审批文件落 `~/.config/nav/approvals/`，部署日志追加 `logs/deploy.log` |

**关键洞察**：这套机制的设计前提是「**AI 会执行部署，但 AI 不能自己批准自己**」。
AI 没有能力伪造一份"人确认过"的文件，且审批内容与待执行动作**精确绑定**、**限时有效**——
所以 AI 即使误判或自作主张，也过不了门禁。

> 对照 disk-clean：**发布流程零门禁**——`publish-release.ps1` 谁都能直接跑。
> 本仓库的实际经历就是证据：最近几轮全部由 AI 直接执行发布，没有任何人工确认环节。

### 1.3 声明式配置 + 凭据分离

| 文件 | 内容 | 是否入库 |
|---|---|---|
| `nav.config.json` | 拓扑：服务器、Nacos、services[]（jar / remoteDir / composeSvc / **port** / **rollPort** / **healthPath**） | ✅ 入库 |
| `nav.secrets.json` | 凭据（SSH key / Nacos 密码 / DB 密码） | ❌ gitignore |
| `~/.config/nav/credentials.json` | 全局凭据（优先于项目级） | ❌ 用户目录 |

- **服务清单是声明式的**：部署工具读它驱动，不再各处硬编码。
- **每个服务显式声明健康检查路径**——部署后据此轮询判定成败。
- 凭据红线：只在 `core/credentials` 读取，**永不输出**。

> 对照 disk-clean：**没有任何声明式清单**。仓库名、包名、资产名、验证命令散落在
> `publish-release.ps1` / `build-installer.ps1` / `README` / `docs` 里，实测硬编码出现：
> `disk-clean-win-x64` × 29、`disk-clean-setup` × 17、`disk-clean-cli` × 9、owner × 5。

### 1.4 自检与体检

- `nav doctor` —— 依赖自检 + **配置校验 + 凭据校验**（新环境第一件事）。
- `nav health -u <url> | -c <container>` —— 健康轮询。
- `nav inspect [-d days]` —— 线上体检。

> 对照 disk-clean：**除 `publish-release.ps1` 的第 0 步外没有任何自检入口**。
> 本仓库的实际经历即为证据：本轮踩过的坑包括 npm token 失效（401）、
> GH_TOKEN 未设置、代理挂掉（`push.ps1` 因此误报成功）——**这三件事 doctor 能一次性全暴露**。

### 1.5 版本管理与发版工具

- `nav dev init/add/done/status/check/set-status/sync` —— 版本管理状态机。
- `nav analyze [--from <tag>]` —— **版本变更分析**：commit 分类 + 接口级 + 代码级 + 有效行数，
  可输出 JSON 供 AI 生成变更记录，并给出 **S/M/L 级别**。
- `nav release -v <ver> [-l <level>]` —— **发版审批清单**。

> 对照 disk-clean：有 `bump-version.js`（只做版本号改写），
> **没有变更分析**（本轮的 CHANGELOG 补写完全靠人工读 `git log`）、**没有发版清单工具**。

### 1.6 发版指南文档化（每次都写一份）

`deploy/release-guide.md` 的结构值得直接借：

```
一、本次上线内容（commit 区间 + 分类表）
二、测试状态（各阶段用例数）
三、上线前准备清单（DB / 配置 / 服务器 / 回滚预案 —— 全是 - [ ] 勾选项）
四、上线步骤（可复制的命令）
五、上线后验证清单（- [ ] 勾选项，含预期值）
六、风险与回滚（风险表 + 回滚命令）
```

> 对照 disk-clean：有**通用**的 `RELEASE-PLAYBOOK.md` 与**面向用户**的 `RELEASE_NOTES-v*.md`，
> 但**没有"本次发版的具体操作指南"**——准备清单、回滚预案、上线后验证清单都在人脑子里。

### 1.7 文档同步（doc-sync skill）

navigator 把"改代码必须同步文档"做成 skill，并规定同步范围。

> 对照 disk-clean：**无强制机制**，且已经实际漂移多次：
> README 展示的建议输出与实现不符（`[organize-folders] 目录整理建议` vs 实际 `[junk-temp] junk-temp`）、
> README 提及的建议类型已不存在、v0.7.0 我本人在工具描述里承诺了 3 个死配置。

### 1.8 ⚠️ 关键教训：**红线到底有多硬**（最值得记住的一节）

对 navigator 逐条核对"约束是**怎么被强制执行**的"之后，结论比表面看到的弱得多：

| 机制 | 声称 | **实际强度** |
|---|---|---|
| `nav deploy` 审批门禁 | 必须审批 | ✅ **真硬**：脚本内校验，失败 `exit 1`，且 **`--yes` 不能代替审批**（显式抛"部署被拦截"） |
| 运维凭据红线（不手写密码/不回显） | 红线 | ⚠️ **半硬**：`core/credentials.ts` 是唯一读取入口（架构约束），但"AI 不手写 `-pw`"**只靠文档与自觉**，无扫描器、无 CI |
| `deploy-guard` 插件拦截 | 有插件会拦 | ❌ **已失效**：其正则只匹配**已删除的旧脚本** `deploy.ps1`/`ops.ps1`，**不匹配现役 `nav deploy`** |
| 文档同步约束 | 强制同步 | ❌ **纯约定**：映射表 + 提交前自查，**无任何自动化检查器** |
| CI 承担红线 | — | ❌ CI 只构建发制品，测试"由 SOP 规定人工保证" |

**三条可直接照搬到 disk-clean 的结论：**

1. **只有"脚本级拦截"是真的。** 文档写红线 ≠ 有红线。
   **本项目已经犯过同类错**：v0.7.0 我在 MCP 工具描述里承诺了 3 个从未实现的配置项——
   文件里写着"支持"，代码里没有。**这正是"文档承诺 vs 实际能力"脱节的同一病症。**
2. **必须区分"人批准"与"AI 自我批准"。** navigator 的设计前提是"AI 会执行，但 AI 不能自己批准自己"。
   disk-clean 现状：MCP 的破坏性工具要 `confirm:true`——**这个 `true` 是 AI 自己填的**，
   等价于自我批准（客户端弹窗才是人的确认，但服务端不校验这个区别）。
   发布流程更是**零门禁**：本仓库最近几轮**全部由 AI 直接执行发布**。
3. **不要制造假安全感。** navigator 的失效插件是最典型的反面教材：
   团队以为"有插件拦截"，实际主链早已不受保护。**要么让脚本门禁成为唯一事实来源，
   要么别声称有防护。**

> **本项目可做得比参考项目更好的一点**：navigator 的 doc-sync **没有自动化检查**，
> 纯靠 AI 自查。而 disk-clean 有 12 套件测试基础设施，完全可以加一个
> **文档一致性守门测试**（S7）——把"约定"升级为"脚本级拦截"。
> 这不是照抄，是把它的弱点补掉。

### 1.9 ⚠️ 第二轮核对：上面那张表**有一行是错的**（2026-09-12 追加）

§1.8 的结论基于"逐条核对约束怎么被强制执行"。之后又对参考项目的流程工具专门做了一次
安全评审（18 项发现，见 `D:\学习\newCode\navigator\docs\nav-tooling-review-2026-09-12.md`），
其中若干条直接修正了本文件此前的判断：

| 机制 | §1.8 的判断 | **复核后的实际强度** |
|---|---|---|
| `nav deploy` 审批门禁 | ✅ 真硬 | ⚠️ **半硬**：脚本级拦截是真的（`--yes` 确实代不了审批），但审批文件是**明文 JSON，无签名、无来源校验**——能写文件的代理自己写一份就放行了。而且交互式批准把版本写成 `"manual"`，这份审批永远不可能与真实版本匹配，**版本绑定对人这条路径其实是失效的** |
| 运维凭据红线 | ⚠️ 半硬（靠文档与自觉） | ❌ **工具自身在违反**：`core/ssh.ts` 用 `-pw` 把 SSH 密码放进进程命令行，而"不把密码放到命令行"正是它红线里的第一条 |
| CI 承担红线 | ❌ CI 只构建发制品 | ❌ **更弱**：`.nav` 自己的 6 个测试文件（含 `approval.test.ts` 的 10 个用例）**从不在 CI 执行**。所以"审批门禁有测试"也是一层假安全感——测试存在，但永远不跑 |

另外两个教科书级的"假通过 / 自伤"缺陷，值得当作负面清单记住：

- **断言吞掉异常**：版本断言把校验包在 `try/catch` 里，`catch` 之后只打印，没有把结果置为失败。
  于是断言失败时流水线照样绿——**校验代码本身成了假绿的来源**。
- **工具把服务器杀掉**：MCP 的部署工具在缺少审批文件时会去读 stdin 等确认，读不到就
  `process.exit(1)`。而 MCP 的 stdin **就是协议通道**，"调用一个工具"因此会直接终止整个 server。

> **对 disk-clean 计划的直接影响：S4 不能照抄它的设计。**
> 原计划里的"版本精确匹配 + 30 分钟时效 + `--yes` 不得代替审批"三条是对的，但不够——
> 它们拦不住"**审批与产物脱钩**"（批准 A、发出去 B）。因此 S4 的实施要求增加：
>
> 1. **审批绑定每个产物的 sha256**，而不只是版本号字符串。批准的是"这些字节"，
>    重新构建后哈希变、审批自动失效。这是与参考项目最实质的差别。
> 2. 版本精确匹配，**明确拒绝** `all` / `manual` / 通配——参考项目正是被 `manual` 害了。
> 3. 审批文件解析失败即失败，**绝不"读不出来就放行"**。
> 4. 没有 `--yes` / `--force` / `--skip-approval`；这些参数被**显式拒绝并说明原因**。
> 5. **把能力边界写进文档**：本机文件门禁拦不住有写权限的代理。不写清楚就是在制造假安全感。
>
> S7 的范围也因此扩大：除了"文档数字与实现一致"，还必须包含
> **"测试文件是否注册进 `test/all.js`"**——参考项目那 6 个永远不跑的测试正是这一类。
> S9 同理：断言必须**真的打包一次并运行产物**来验证，而不是断言"脚本里写了 `--define`"。
> 后者证明的是意图，不是结果，正是参考项目"断言吞异常"的同类错误。

> **仍然未解决的一项（诚实记录，不要假装已处理）**：本仓库 MCP 的破坏性工具要求
> `confirm:true`，而**这个 `true` 是 AI 自己填的**，等价于自我批准。服务端无法区分
> "AI 填的 true"和"人在客户端点了确认"，所以这层确认只能依赖 MCP 客户端的弹窗 UI。
> 现状不改，但**不再声称它是一道人机确认闸门**——那样说就是假安全感。

## 3. 明确**不移植**（避免生搬硬套）

这些依赖 navigator 的**多服务 + 服务器拓扑**前提，对单机桌面工具无意义：

| 机制 | 为什么不适用 |
|---|---|
| `services[]` 多服务编排、`rollPort` 滚动部署 | disk-clean 是单机单进程，没有"多实例灰度"概念 |
| SSH 隧道、Nacos、Redis 远程操作 | 无远程基础设施 |
| `nav db`（本地库对齐线上、SQL 合并、内容迁移） | 无数据库 |
| `nav health -c <container>` / `nav inspect` | 无容器、无线上服务 |
| `nav ops login` / `decrypt-key` | 无鉴权服务、无加密密钥 |
| `nav tunnel` | 无内网数据库需要隧道 |
| `nav project init`（多项目脚手架） | 只维护一个项目 |

**但其中一条思想要保留**：`nav.config.json` 的**"声明式 + 带健康检查路径"** 这个形式——
disk-clean 的对应物是"发布资产清单 + 每项的体积/哈希校验"，这是同一思想的单机版本。

## 4. 实施计划

### 阶段一：把流程从文档搬进工具（✅ 已实施）

| 项 | 产物 | 验收 | 状态 |
|---|---|---|---|
| S1 | `scripts/dev.js doctor` | 在**缺 token** 与**代理关闭**两种情况下都能明确指出问题与修复命令 | ✅ 已验证（缺 token 时报 2 项阻塞 + 修复命令） |
| S2 | `scripts/dev.js verify` | 一条命令跑完语法/12 套件/ASCII/版本一致性/exe e2e，退出码可作门禁 | ✅ 已验证（5 步全通过，约 15 秒） |

> **为什么放在 `scripts/` 而不是 `bin/disk-clean.js`**：`bin/` 是**要发布给用户的 CLI**
> （npm 的 `files` 只含 `bin`/`lib`，`scripts/` 既不进 npm 包也不进 SEA exe）。
> 开发与发布工具不该污染产品入口，但**统一成一条命令**——这是 navigator 的核心教训。

### 阶段二：脚本级门禁（**优先级最高**，对应 §1.8）—— ✅ 已实施

### 实施中自己踩的坑（留档，因为它们都是"闸门看起来在工作"的假象）

这几处都是我自己在第一版实现里犯的错，值得记下来——它们的共同点是
**门禁没有报错，只是报了错的东西**，比崩溃更难发现：

1. **把"说明文字里的键名"当成"代码在读"**：死配置检测一开始直接在源码原文上搜键名，
   而 `lib/mcp/tools.js` 的描述里恰好写着"还存在 `retention.reports` / `junkRules` / `organizeRules`
   但尚未读取"——于是这三项被判成"已接线"，门禁反过来报告"登记过期"。
   **文档里提到一个键 ≠ 代码里读了这个键**，必须先剥离注释与字符串字面量再匹配。
2. **剥离器被正则字面量带跑**：剥字符串的实现没识别正则，而 `lib/engine-core.js` 里有 `/["']/` 这种
   带引号的正则，于是扫描器从那里"开始一个字符串"，**吞掉几百行代码**，结果所有配置键都被判成死。
   修完还补了一个**剥离器自检**——否则"剥离器坏了"会伪装成"所有配置都死了"。
3. **空对象被当成中间节点**：`organizeRules: {}` 在展开叶子路径时被当作分支递归下去，
   得到空结果，于是这一项**从未进入检查集合**，表现却是"登记过期"这种看起来无关的报错。
4. **比错了对象**（与参考项目 C2 同类）：指纹断言最初比较的是"**当前工作树**是否干净"，
   而不是"**产物自述的构建状态**"。后果是打完包再开下一版开发，旧产物就被判失效。
   正确语义是：产物自述 `dirty=false` + `commit == HEAD` 才说明它等于当前源码；
   "当前工作树是否已全部提交"是发布时的另一条独立要求，只在显式要求时判定。
5. **统计口径说谎**：`dev analyze` 起初只看已提交区间，**漏掉整个未提交的工作区**——
   而"这次要发的东西有多大"恰恰主要看工作区，漏掉只会把级别算低、让人少做验证（危险方向）。
   改完之后又把未提交文件一并计入"提交数"，措辞失真，再拆成"提交 N 个 + 变更文件 M 个（其中 K 个尚未提交）"。

> **这一阶段的共同点**：三项都是**脚本级拦截**，而不是又写一段文档。
> 依据 §1.8 的教训——参考项目里唯一真正防住事故的就是脚本门禁，
> 而它失效的插件正是"以为有防护"的反面教材。

## 6. 参考项目的 5 条精选（若只能记 5 条）

1. **不可逆动作必须有人工审批闸门，且脚本级硬拦**——`--yes` 不得代替审批；
   这是整套 SOP 唯一真正防住事故的机制，且完全不依赖拓扑。
2. **凭据单一入口 + 永不回显**——一个 gitignore 的 secrets 文件 + 一个唯一读取模块；
   安全靠架构而非自律。
3. **净变更行数 → 变更级别 → 验证深度分级**（S<500 / M>500 / L>1000）——
   单人项目最怕流程太重被弃用，分级才可持续。
4. **制品可验证：产物带 version/commit 指纹，发布后断言与源码一致**——
   根治"假成功 / 发了旧包"。
5. **改动类型 → 必同步文档映射表 + 同 commit**——半年后唯一的记忆就是文档。

> 外加一条零成本的：**"没有新鲜的验证证据，不许宣称完成"**，
> 直接压制 AI 的"看起来好了"式假完成。
